# Design decisions

## ADR-001 — Poseidon (SW backend): optimized form, per-field Montgomery tables

Date: 2026-11-25. Status: amended by ADR-002 (sparse rounds are optional, off by
default). Version: v0.2.6.

### Context

On a Ledger Nano S Plus built with the SW backend, Poseidon is bounded by
256-bit Montgomery multiplications (about 31 µs each, fitted on the
measurements of PR #3). The textbook rounds spend most of them in three
places: a dense t x t matrix in each of the 56 to 64 partial rounds, one
conversion to Montgomery form per round constant and per matrix coefficient,
and a generic exponentiation for the S-box of the partial rounds.

Flash is the scarce resource: a Ledger app links in 400 KB.

### Decision

1. Run the permutation in the optimized form of the Poseidon paper
   (appendix B), with the table layout of circomlibjs
   `poseidon_constants_opt` (C, S, M, P).
2. Store every table element in Montgomery form (x * 2^256 mod q), as 8
   little-endian 32-bit limbs, the in-memory format of `zkn_mont256`. Tables
   are plain `uint32_t` arrays: no byte order assumption, no conversion, no
   copy in RAM.
3. One table per (field, arity). The optimized constants come from matrix
   inverses, so they depend on the field. `zkn_poseidon_init` looks the table
   up by the modulus of the Montgomery context and fails when there is none.
4. Tables are generated by `tools/gen_poseidon_opt.py` from the instance
   parameters alone (Grain LFSR, Cauchy matrix, optimization), and checked
   against the circomlibjs files with `--check`. Nothing is copied from a
   third-party file.
5. Two compile-time masks, `ZKN_POSEIDON_ARITIES` and
   `ZKN_POSEIDON_BLS12381_ARITIES`, choose the tables that are linked.

### The BLS12-381 table

`zkn_eddsa.c` and `zkn_frost.c` call Poseidon-5 with the Montgomery context of
the curve. On Bandersnatch that context is the BLS12-381 scalar field, and the
library has always hashed there with the integers generated for BN254. This is
not a hadeshash BLS12-381 parameter set, but signatures depend on it. The
generator therefore emits a second table for Poseidon-5: the same integers,
optimized and converted over that field. Outputs are unchanged. A proper
BLS12-381 instance would be a new entry in `INSTANCES`.

### Consequences

* 3.0 to 3.6 times fewer multiplications per hash, 2 KB less per context.
* 186 KB of flash with every table, against 85 KB. A build that lists its
  arities gets back to that size or below (see STATUS.md).
* The SW Poseidon is tied to the radix of `zkn_mont256` (R = 2^256). The cx_bn
  implementation (`zkn_poseidon_constants.c`) is untouched.
* A modulus without a table is now an error at init instead of a hash with
  constants that were not generated for it.

### Alternatives not retained

* Keeping the textbook rounds as a fallback for other moduli: it needs the
  plain constants too, about 83 KB more.
* Regenerating constants with Grain at run time for other moduli: no flash,
  but 0.7 s per Poseidon-5 on the device.
* Byte tables loaded with `zkn_bn_init`: one copy per use, and the byte order
  of the limbs has to be handled.
* A table of pointers indexed by arity: constant pointers need relocation in
  position-independent Ledger apps. The lookup is a `switch`.

## ADR-002 — Poseidon tables: dense partial rounds by default, sparse rounds per arity

Date: 2026-11-25. Status: accepted. Version: v0.2.7.

### Context

ADR-001 took the fully optimized form: 186 KB of Poseidon objects, of which
the sparse matrices are the bulk (RP x (2t - 1) elements per arity). That is
close to half of what a Ledger app can link.

The optimized form is two independent transformations. Moving the round
constants through the linear layer makes the table smaller: a partial round
keeps one constant out of t. Only the sparse matrices cost flash, and they can
be applied to any number k of partial rounds, counted from the last.

### Decision

1. Default tables use k = 0: pushed constants, dense MDS matrix in every
   round. A table is t RF + RP + t^2 elements.
2. k is chosen per (field, arity) when the tables are generated
   (`tools/gen_poseidon_opt.py --sparse`, or `SPARSE` in the script). A table
   with k > 0 carries the matrix PT of the round before the sparse ones and
   k x (2t - 2) coefficients.
3. The corner coefficient of a sparse matrix is M[0][0] in every round. It is
   not stored again: the code reads it from the MDS matrix.
4. The C code handles any k. `zkn_poseidon_opt_table` returns k with the
   table, `zkn_poseidon` runs RP - k dense partial rounds, then k sparse ones.

### Consequences

* Default build: 35 KB of Poseidon objects, against 85 KB before this work,
  for 1.3 (Poseidon-7) to 2.8 (Poseidon-1) times fewer multiplications.
* A sparse round costs 64 (t - 1) bytes and saves (t - 1)^2 multiplications.
  The return grows with the arity, so flash is best spent on large and
  frequently hashed arities. k = RP for all gives 171 KB and 3.0 to 3.6 times
  fewer multiplications.
* The sparse layer is compiled in but not executed with the default tables.
  It was validated with k = RP and with mixed values of k (unit tests, random
  comparison with circomlibjs, address and undefined-behaviour sanitizers).
  A build that enables it has to rerun `make test` and `make poseidon-diff`.

### Alternatives not retained

* One reduction per dot product (accumulate the t products of a matrix row on
  17 limbs, then a single Montgomery reduction): 64t + 72 limb
  multiplications instead of 136t. A host prototype gives 18 to 38% per hash with
  dense rounds, from 3 inputs up, with no table. Left out of this version: on
  a build that uses the assembly multiplication (`ZKN_MONT256_ASM`) the
  accumulation has to be written in Thumb-2 assembly as well.
